<objective>
Make streaming failure recovery safe and deterministic by preventing retries/failovers after any meaningful output (including tool-call state) has been emitted, and by enforcing attempt budgets across retries/failovers without being reset by recursive calls.

Purpose:
- REL-03: Streaming sessions must not duplicate output or corrupt tool-call state when a backend fails mid-stream.
- REL-04: Failover must preserve request context and avoid non-deterministic side effects; budgets must be enforced across retries/failovers (no infinite recursion / budget reset).

Today’s key gaps:
- `BackendCompletionFlow.call_completion()` initializes `start_time` and `attempted_backends` locally each call; recursive retry/failover resets budgets.
- `content_started` is always initialized False and never updated, making failure strategy unsafe for streaming semantics.
- `BackendStreamingResponseHandler` supports empty-stream retry, but does not safely handle stream exceptions (disconnects/timeouts) relative to “meaningful output already emitted”.

Output: A persisted stream recovery budget (start time + attempted backends + meaningful-output flags) stored in `RequestContext.extensions`, and streaming handler logic that retries only before meaningful output and otherwise emits a terminal error chunk.
</objective>
