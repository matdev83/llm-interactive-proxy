# Requirements Document

## Introduction

ProxyMem is a proxy-based memory layer for LLM agents that provides cross-session context persistence. By operating at the proxy layer between clients and LLM backends, ProxyMem captures session data, generates structured summaries via LLM analysis, and enriches future requests with relevant historical context. This enables any agent connected to the proxy to benefit from improved historical awareness without requiring client-side modifications.

The feature operates through three main mechanisms:
1. **Session Capture**: Recording session interactions as they pass through the proxy
2. **Session Analysis**: Using a designated LLM to generate structured summaries after session completion
3. **Context Injection**: Enriching new session requests with relevant historical context retrieved from the database

## Glossary

- **ProxyMem**: The proxy-based memory layer feature that provides cross-session context persistence
- **Session**: A conversation between a client/agent and an LLM backend, identified by a unique session ID
- **Session Summary**: A structured analysis of a completed session generated by an LLM, including scope, goals, modified files, and completion status
- **Context Provider Model**: The LLM model designated to retrieve and prepare relevant historical context for new sessions
- **Summary Generator Model**: The LLM model designated to analyze completed sessions and generate structured summaries
- **Memory Database**: SQLite database storing session metadata and summaries
- **Context Injection**: The process of adding historical context as a virtual message between system prompt and first user message
- **Memory State**: The current enabled/disabled status of ProxyMem data gathering for a session
- **Summary Schema Version**: Version identifier for the XML schema used in session summaries
- **Redaction Pattern**: Configurable rule (e.g., regex) used to mask sensitive data before model calls or persistence
- **Analysis Queue**: Bounded background queue that holds completed sessions awaiting summarization
- **Project Root**: The detected root directory of the project for the current session (from deterministic or non-deterministic discovery)
- **Project ID**: Stable identifier mapped to a `(user_id, project_root)` pair for efficient storage and lookup
- **User Identity**: Authenticated identifier (e.g., SSO subject/UUID) used to scope memory access and storage
- **Tenant/Group**: Optional higher-level grouping (e.g., org, project, team) used to enforce access controls on memory records

## Requirements

### Requirement 1: Global Feature Availability Control

**User Story:** As a system administrator, I want to control whether ProxyMem is available at all on the proxy instance, so that I can ensure the feature is only active in environments where it is appropriate.

#### Acceptance Criteria

1. WHERE the `memory_available` configuration option is set to `true`, THE ProxyMem system SHALL allow activation of memory features through interactive commands or session-specific configuration
2. WHERE the `memory_available` configuration option is set to `false` or unspecified, THE ProxyMem system SHALL reject all attempts to enable memory features and SHALL NOT capture any session data
3. WHEN a user attempts to use `!/memory-on` command while `memory_available` is `false`, THE ProxyMem system SHALL return an error message indicating the feature is not available on this proxy instance
4. THE ProxyMem system SHALL support configuration of `memory_available` through CLI flag (`--memory-available`), environment variable (`MEMORY_AVAILABLE`), and configuration file entry (`memory.available`)
5. THE ProxyMem system SHALL apply configuration precedence in order: CLI flag overrides environment variable overrides configuration file

### Requirement 2: Default Memory State Control

**User Story:** As a system administrator, I want to configure the default state of memory gathering when the feature is globally available, so that I can control whether sessions automatically participate in memory collection.

#### Acceptance Criteria

1. WHERE `memory_available` is `true` AND `memory_default_enabled` is set to `true`, THE ProxyMem system SHALL enable memory gathering by default for new sessions
2. WHERE `memory_available` is `true` AND `memory_default_enabled` is set to `false` or unspecified, THE ProxyMem system SHALL disable memory gathering by default for new sessions
3. THE ProxyMem system SHALL support configuration of `memory_default_enabled` through CLI flag (`--memory-default-enabled`), environment variable (`MEMORY_DEFAULT_ENABLED`), and configuration file entry (`memory.default_enabled`)
4. WHEN `memory_available` is `false`, THE ProxyMem system SHALL ignore the `memory_default_enabled` setting

### Requirement 3: Session-Level Memory Control

**User Story:** As a user, I want to control whether my current session participates in memory gathering, so that I can choose when my interactions are recorded.

#### Acceptance Criteria

1. WHEN a user sends the `!/memory-on` command AND `memory_available` is `true`, THE ProxyMem system SHALL enable memory gathering for the current session and return a confirmation message
2. WHEN a user sends the `!/memory-off` command, THE ProxyMem system SHALL disable memory gathering for the current session and return a confirmation message
3. WHEN memory gathering is disabled mid-session via `!/memory-off`, THE ProxyMem system SHALL stop capturing new interactions but SHALL retain any data already captured during the session
4. WHEN a user sends `!/memory-status` command, THE ProxyMem system SHALL return the current memory gathering state for the session
5. THE ProxyMem system SHALL persist the memory state change only for the duration of the current session

### Requirement 4: Session Data Capture

**User Story:** As a system operator, I want the proxy to capture session interaction data when memory is enabled, so that sessions can be analyzed and summarized later.

#### Acceptance Criteria

1. WHILE memory gathering is enabled for a session, THE ProxyMem system SHALL capture user prompts and assistant responses passing through the proxy
2. WHILE memory gathering is enabled, THE ProxyMem system SHALL record session metadata including session ID, user ID, session start timestamp, client/agent name, and backend:model used
3. WHEN capturing session data, THE ProxyMem system SHALL store data in memory until session completion to minimize I/O overhead
4. THE ProxyMem system SHALL implement a maximum buffer size for in-memory session data to prevent memory exhaustion

### Requirement 5: Session Completion Detection

**User Story:** As a system operator, I want the proxy to detect when a session has ended, so that session analysis can be triggered automatically.

#### Acceptance Criteria

1. WHEN a session has no activity for a configurable timeout period (default: 30 minutes), THE ProxyMem system SHALL consider the session complete
2. WHEN a client explicitly closes a connection or session, THE ProxyMem system SHALL consider the session complete
3. WHEN a session is marked complete AND memory gathering was enabled, THE ProxyMem system SHALL queue the session for background analysis
4. THE ProxyMem system SHALL support configuration of the session timeout through `memory.session_timeout_minutes` configuration option

### Requirement 6: Session Summary Generation

**User Story:** As a system operator, I want completed sessions to be analyzed by an LLM to generate structured summaries, so that the information can be efficiently retrieved later.

#### Acceptance Criteria

1. WHEN a session is queued for analysis, THE ProxyMem system SHALL call the configured summary generator model with the session transcript
2. WHEN generating a summary, THE ProxyMem system SHALL instruct the LLM to produce a structured XML response that satisfies Requirement 12 (covering session scope, main goals, modified files, completion status, remaining gaps, operations performed, and key evidence)
3. WHEN generating a summary, THE ProxyMem system SHALL also request a one-sentence title for the session
4. WHEN summary generation completes successfully, THE ProxyMem system SHALL store the summary in the memory database
5. IF summary generation fails, THE ProxyMem system SHALL log the error and retry up to 3 times with exponential backoff
6. THE ProxyMem system SHALL process summary generation asynchronously in a background task to avoid blocking proxy operations
7. THE ProxyMem system SHALL support configuration of the summary generator model through CLI flag (`--memory-summary-model`), environment variable (`MEMORY_SUMMARY_MODEL`), and configuration file entry (`memory.summary_model`) using format `backend:model`
8. THE ProxyMem system SHALL support configuration of a custom prompt file for the summary generator through CLI flag (`--memory-summary-prompt`), environment variable (`MEMORY_SUMMARY_PROMPT`), and configuration file entry (`memory.summary_prompt`) accepting `.txt` or `.md` file paths
9. WHEN no custom summary prompt file is configured, THE ProxyMem system SHALL use a built-in default prompt optimized for session summarization
10. THE ProxyMem system SHALL validate that the LLM response is well-formed XML that matches the required schema and SHALL retry with a corrective system message when validation fails
11. WHEN session data lacks evidence for a requested field (e.g., touched files or commits), THE ProxyMem system SHALL populate the field with explicit sentinel values such as `UNKNOWN` or `NONE` rather than inventing data
12. WHEN the session transcript exceeds configured analysis limits, THE ProxyMem system SHALL chunk and summarize incrementally to preserve ordering and avoid exceeding model limits (see Requirement 13)
13. AFTER a summary is persisted, THE ProxyMem system SHALL discard raw session transcripts from memory and SHALL NOT persist the full transcript to the database
14. THE ProxyMem system SHALL enforce a maximum completion token budget for summary generation requests, configurable via `memory.summary_completion_tokens` (default: 10,000 tokens) and SHALL truncate or constrain generations to this limit
15. IF a model response exceeds the allowed size or retries still fail, THE ProxyMem system SHALL apply middle-out compression (preserve start/end, compress middle) to produce an XML summary within the token budget

### Requirement 7: Memory Database Storage

**User Story:** As a system operator, I want session summaries stored in a persistent database, so that historical context survives proxy restarts.

#### Acceptance Criteria

1. THE ProxyMem system SHALL use SQLite as the storage backend for session summaries
2. THE ProxyMem system SHALL store the following fields for each session record: user_id (required), tenant/group identifier (optional), project_id (optional), project_root (optional), session_id, session_start_timestamp, client_agent_name, backend_model_used, session_title, scope, full_session_analysis, completion_status, goals, remaining_tasks, open_questions, touched_files, git_operations, key_decisions, operations_performed, tests_run, errors, branch, head_sha, risks_or_warnings, evidence, created_at, summary_version
3. WHEN storing a session record, THE ProxyMem system SHALL create indexes on user_id and session_start_timestamp for efficient querying
4. THE ProxyMem system SHALL support configuration of the database file path through `memory.database_path` configuration option (default: `./var/memory.sqlite3`)
5. WHEN the database file does not exist, THE ProxyMem system SHALL create it with the appropriate schema on first use
6. THE ProxyMem system SHALL implement database connection pooling to handle concurrent access
7. THE ProxyMem system SHALL retain the structured XML payload alongside the parsed fields to allow re-hydration and debugging while keeping it bounded in size
8. THE ProxyMem system SHALL NOT persist full session transcripts; only the structured summary and minimal metadata SHALL be stored

### Requirement 8: Context Retrieval and Injection

**User Story:** As a user, I want my new sessions to automatically receive relevant context from my previous sessions, so that the LLM has awareness of my prior work.

#### Acceptance Criteria

1. WHEN a new session begins with memory gathering enabled AND the user has prior session records, THE ProxyMem system SHALL query the context provider model to identify relevant historical context
2. WHEN querying for context, THE ProxyMem system SHALL provide the context provider model with recent session summaries for the user (and tenant/project when available) and the current user prompt
3. WHEN the context provider model returns relevant context, THE ProxyMem system SHALL inject it as a virtual message between the system prompt and the first user message
4. THE ProxyMem system SHALL limit context injection to a configurable maximum token count (default: 2000 tokens) to preserve context window space
5. IF context retrieval fails or times out, THE ProxyMem system SHALL proceed with the request without injected context and log a warning
6. THE ProxyMem system SHALL support configuration of the context provider model through CLI flag (`--memory-context-model`), environment variable (`MEMORY_CONTEXT_MODEL`), and configuration file entry (`memory.context_model`) using format `backend:model`
7. THE ProxyMem system SHALL support configuration of a custom prompt file for the context provider through CLI flag (`--memory-context-prompt`), environment variable (`MEMORY_CONTEXT_PROMPT`), and configuration file entry (`memory.context_prompt`) accepting `.txt` or `.md` file paths
8. WHEN no custom context prompt file is configured, THE ProxyMem system SHALL use a built-in default prompt optimized for context retrieval
9. THE ProxyMem system SHALL support configuration of the maximum number of recent sessions to consider through `memory.max_sessions_to_consider` configuration option (default: 10)
10. WHEN selecting context, THE ProxyMem system SHALL rank summaries by a relevance+recency strategy (e.g., scoring on feature/file/component overlap and recency) and inject only those above a configurable relevance threshold (`memory.context_relevance_threshold`, default: 0.5); low-confidence context SHALL be omitted
11. WHEN no context is injected (due to low relevance, timeout, backpressure, missing project, or token cap), THE ProxyMem system SHALL insert a minimal marker message (e.g., `[NO_PRIOR_CONTEXT_PROVIDED]`) so downstream agents know to rely solely on current input

### Requirement 9: Context Injection Format

**User Story:** As a developer, I want the injected context to be clearly formatted, so that the LLM can distinguish historical context from the current conversation.

#### Acceptance Criteria

1. WHEN injecting historical context, THE ProxyMem system SHALL wrap the context in a clearly delimited format with markers indicating it is historical context
2. WHEN injecting context, THE ProxyMem system SHALL include a brief explanation that this information comes from prior sessions
3. THE ProxyMem system SHALL format the injected message with role "user" to maintain compatibility with all LLM backends
4. THE ProxyMem system SHALL support configuration of a custom context injection template through `memory.context_template` configuration option

### Requirement 10: Database Maintenance

**User Story:** As a system administrator, I want automatic cleanup of old session records, so that the database does not grow unbounded.

#### Acceptance Criteria

1. THE ProxyMem system SHALL support configuration of a retention period through `memory.retention_days` configuration option (default: 90 days)
2. WHEN the proxy starts, THE ProxyMem system SHALL schedule a periodic cleanup task to remove session records older than the retention period
3. WHEN deleting old records, THE ProxyMem system SHALL log the number of records removed
4. THE ProxyMem system SHALL run cleanup operations during low-activity periods to minimize performance impact

### Requirement 11: Default Prompts

**User Story:** As a system operator, I want high-quality default prompts for the summary and context models, so that the system works effectively out of the box.

#### Acceptance Criteria

1. THE ProxyMem system SHALL include a built-in default prompt for session summarization that instructs the LLM to emit the XML format from Requirement 12 and extract: session title, scope, main goals, remaining tasks, modified files, git operations, task completion status, and key decisions made
2. THE ProxyMem system SHALL include a built-in default prompt for context retrieval that instructs the LLM to: analyze the current user prompt, identify relevant prior sessions, and synthesize a concise context summary
3. THE ProxyMem system SHALL store default prompts in the `config/prompts/` directory as `.md` files for easy review and customization
4. WHEN loading a custom prompt file, THE ProxyMem system SHALL validate that the file exists and is readable, returning an error at startup if validation fails
5. THE ProxyMem system SHALL support template variables in prompt files including `{session_transcript}`, `{user_prompt}`, `{session_summaries}`, `{max_tokens}`, `{summary_schema_version}`, `{summary_prompt_version}`, `{session_id}`, `{user_id}`, `{tenant_id}`, `{project_id}`, `{project_root}`, `{analysis_timestamp}`, `{model}`, `{branch}`, `{head_sha}`, `{deterministic_file_edits}`, and `{deterministic_git_commits}`

### Requirement 12: Structured Session Summary Format (XML)

**User Story:** As a system operator, I want session summaries to be emitted in a deterministic, machine-parseable XML format, so that downstream consumers can reliably extract session facts without post-processing heuristics.

#### Acceptance Criteria

1. WHEN generating a summary, THE ProxyMem system SHALL require a well-formed XML payload with root element `<session_summary>` and SHALL reject any response containing additional natural-language preamble or postamble
2. THE XML payload SHALL include the following child elements: `<title>` (one sentence), `<scope>...</scope>`, `<main_goals><goal>...</goal></main_goals>`, `<completion_status>` (enum: completed|partial|abandoned), `<remaining_tasks><task status=\"open|blocked\">...</task></remaining_tasks>`, `<open_questions><item>...</item></open_questions>`, `<touched_files><file status=\"created|modified|deleted\">path</file></touched_files>`, `<git_operations><operation type=\"commit|branch|merge\" ref=\"...\">details</operation></git_operations>`, `<operations_performed><operation>...</operation></operations_performed>`, `<tests_run><test status=\"passed|failed|timeout|skipped\">name or command</test></tests_run>`, `<errors><error>exception or error message</error></errors>`, `<key_decisions><decision>...</decision></key_decisions>`, `<risks_or_warnings><item>...</item></risks_or_warnings>`, `<evidence><item>...</item></evidence>`
3. THE XML payload SHALL include a `<metadata>` block containing `session_id`, `user_id` (if known), `tenant_id` (if known), `project_id` (if known), `project_root` (if known), `analysis_timestamp`, `model`, `prompt_version`, `summary_version`, `branch` (if known), and `head_sha` (if known)
4. WHEN evidence for any field is absent, THE ProxyMem system SHALL populate the field with the literal text `UNKNOWN` or emit an empty collection, never fabricated data
5. THE ProxyMem system SHALL ensure all string content is escaped for XML and SHALL strip markdown or code fences from the output
6. THE ProxyMem system SHALL validate the XML against an XSD or equivalent structural check before persisting or using it for context injection
7. THE ProxyMem system SHALL version the XML schema (e.g., `summary_version`) to allow safe migrations and re-parsing
8. WHEN validation fails, THE ProxyMem system SHALL retry generation with a corrective system message and SHALL log the invalid payload for debugging without leaking user content in plaintext logs

### Requirement 13: Large Session Handling and Idempotency

**User Story:** As a system operator, I want long-running sessions and duplicate completion signals to be handled robustly, so that summaries remain correct and the system does not overload.

#### Acceptance Criteria

1. WHEN a session transcript exceeds a configurable size threshold (characters or tokens), THE ProxyMem system SHALL chunk the transcript and either summarize hierarchically or stream summaries, preserving message order
2. THE ProxyMem system SHALL deduplicate completion events per session_id and SHALL ensure only one summary is persisted per session unless explicitly re-queued
3. WHEN the analysis queue is full or blocked, THE ProxyMem system SHALL apply backpressure (drop or delay according to configuration) without affecting core proxy request/response latency
4. WHEN the service restarts while jobs are in-flight, THE ProxyMem system SHALL resume or requeue pending analyses without producing duplicate records
5. THE ProxyMem system SHALL expose configuration for analysis queue size, per-job timeout, and maximum concurrent analyses

### Requirement 14: Privacy, Redaction, and Data Handling

**User Story:** As a privacy-conscious operator, I want sensitive data protected during capture and summarization, so that ProxyMem does not leak secrets or persist unnecessary content.

#### Acceptance Criteria

1. THE ProxyMem system SHALL support configurable redaction rules (e.g., regex patterns for secrets, access tokens, keys) applied before persisting summaries or logging
2. THE ProxyMem system SHALL avoid storing full transcripts on disk; only structured summaries and minimal metadata SHALL persist beyond session lifetime
3. WHEN logging errors or retries, THE ProxyMem system SHALL avoid including raw user content and instead reference opaque identifiers
4. THE ProxyMem system SHALL allow operators to disable memory for specific users or clients via configuration or ACL hooks to satisfy privacy constraints

### Requirement 15: Observability and Operational Safeguards

**User Story:** As an operator, I want insight into ProxyMem health and the ability to intervene, so that I can keep the system reliable in production.

#### Acceptance Criteria

1. THE ProxyMem system SHALL emit metrics for capture buffer utilization, analysis queue depth, summary generation latency, success/failure counts, and context injection hit-rate
2. THE ProxyMem system SHALL provide structured logs (with session_id and user_id where available) for state transitions, retries, and cleanup operations
3. THE ProxyMem system SHALL expose a lightweight health check that reports memory availability, database connectivity, and worker status
4. THE ProxyMem system SHALL provide an administrative command or API to requeue or regenerate a summary for a given session_id using the latest prompt

### Requirement 16: Backpressure and Resource Protection

**User Story:** As a system operator, I want ProxyMem to degrade gracefully under load, so that memory features never compromise core proxy throughput.

#### Acceptance Criteria

1. WHEN capture buffers or analysis queues exceed configurable limits, THE ProxyMem system SHALL stop capturing additional data for the affected session and SHALL notify via logs or system messages without impacting ongoing proxy traffic
2. THE ProxyMem system SHALL enforce per-request timeouts for summary and context model calls and SHALL fall back to pass-through behavior on timeout
3. THE ProxyMem system SHALL ensure database write failures do not block request handling; failed writes SHALL be retried or dropped according to policy
4. THE ProxyMem system SHALL cap context injection size and skip injection when the cap would be exceeded rather than truncating critical current messages

### Requirement 17: Multi-User Isolation and Access Control

**User Story:** As a security-conscious operator, I want strong isolation between users (and optional tenants/groups) so that no user can access or receive memory data from another user.

#### Acceptance Criteria

1. THE ProxyMem system SHALL require an authenticated `user_id` for all memory operations (capture, analysis, retrieval, injection); sessions without a resolvable user_id SHALL be treated as memory-disabled unless explicitly configured for single-user mode
2. THE ProxyMem system SHALL scope all database reads/writes to the authenticated `user_id` (and tenant/group, if present) and SHALL prevent cross-user access by design (query filters, constraints)
3. THE ProxyMem system SHALL ensure context retrieval and injection only use summaries that match the requesting `user_id` (and tenant/group, if provided)
4. THE ProxyMem system SHALL include the `user_id` (and tenant/group) in summary metadata and logs/metrics for auditability without exposing other users’ data
5. THE ProxyMem system SHALL provide a configuration flag for single-user mode that bypasses user lookup but still enforces isolation by treating all sessions as the same user identity
6. THE ProxyMem system SHALL fail closed: if identity is missing/invalid, memory capture and retrieval SHALL be skipped and a warning logged
7. THE ProxyMem system SHALL support SSO-provided identities and pass them through unmodified as the canonical `user_id`

### Requirement 18: Project-Scoped Context and Discovery Gating

**User Story:** As a multi-project user, I want memory and context limited to the current project so I do not get irrelevant or leaking information from other projects.

#### Acceptance Criteria

1. THE ProxyMem system SHALL enable memory capture and context injection only when project root discovery is enabled and succeeds (deterministic or non-deterministic modes)
2. WHEN project root discovery fails or is unavailable for the current session, THE ProxyMem system SHALL disable context injection (and optionally capture) for that session and log a warning
3. THE ProxyMem system SHALL associate each session summary with a project_id/project_root derived from discovery (when available)
4. THE ProxyMem system SHALL scope context retrieval to summaries matching the same user_id (and tenant_id, if any) AND matching project_id/project_root; summaries from other projects SHALL be excluded even if they belong to the same user
5. THE ProxyMem system SHALL maintain a `user_project_dirs` dictionary (unique on user_id + project_root) to assign stable project IDs for storage and retrieval efficiency

### Requirement 19: Deterministic Tool Event Capture (File Edits & Git Commits)

**User Story:** As a ProxyMem consumer, I want deterministic records of file edits and git commits captured during a session so that summaries reflect actual changes instead of inferred ones.

#### Acceptance Criteria

1. WHILE memory gathering is enabled for a session, THE ProxyMem system SHALL capture deterministic tool events flagged as file editing operations (e.g., apply_patch/write-file/append-file) and accumulate a per-session list of edited file paths, normalized relative to the project root when available (or absolute when not).
2. FOR each recorded file edit event, THE ProxyMem system SHALL attach an action classification (`created`, `modified`, `deleted`, or `unknown`) and deduplicate entries per file path while preserving the most recent action and timestamp for the session.
3. WHILE memory gathering is enabled, THE ProxyMem system SHALL capture deterministic git commit events (e.g., successful `git commit`) and record commit hash, commit message when available, branch (if known), and timestamp in a per-session list.
4. THE deterministic file edit list and git commit list SHALL be stored in session capture data (`SessionData`) and forwarded to the summary generator alongside the transcript.
5. WHEN deterministic lists are present, THE summary generator SHALL include them explicitly in the summary prompt and prefer them as the source of truth for `<touched_files>` and `<git_operations>`, only falling back to transcript inference or `UNKNOWN` when the lists are empty.
6. THE summary generator SHALL submit the deterministic file edits list and git commit list to the summarizing agent in a structured, machine-readable section so the agent cannot omit or hallucinate file paths or commits.
